# Streaming script creation and editing

## Timeout cause and changes

The reported TestCodes folder was resolved correctly. The old coding planner waited for an entire HTTP response with a 120-second read timeout, and the inference worker had a 150-second total limit. This installation's `Qwen3-Coder:latest` is a 30.5B Q4 model running on the CPU. Its loading/prompt processing can outlast those deadlines before a file is created.

Clear single-script requests such as “Create a Python script for alarm in TestCodes folder” now infer the target `alarm.py` and skip separate coding-plan inference. Source still comes from the configured Qwen3-Coder; this is not an alarm template. Explicit existing-file edits already skip plan inference. Ambiguous and multi-file goals retain model planning.

Coding HTTP responses stream incrementally. The coding worker uses a smaller coding-only instruction preamble, adaptive context allocation, a 3,200-token source limit, and the non-thinking ChatML prefix for this imported Qwen3-Coder model. Resolved file/project context, repository instructions, selected skills, relevant procedure guidance and bounded memory remain available. Global PC-name training lookup runs on desktop planning rather than coding source generation.

`brain.coding_timeout_seconds` in [config.json](../config.json) defaults to **900 seconds**, bounded to 120–900. It applies to each coding inference call, including loading and prompt processing. Desktop and general-question deadlines keep their own settings. Stop/cancellation closes the owned worker promptly. Interrupted streaming inference is not automatically retried; a new explicit request can resume an unchanged owned draft. The 15-minute limit is not a promised latency.

## Code appears as it arrives

- **New script:** Jarvis creates the requested file with an incomplete-draft header, then updates its decoded source as tokens arrive, approximately every 100 ms. Python code and escaped characters are decoded from the JSON envelope; raw JSON is not written into the script.
- **Editing:** The existing source stays available while `<filename>.jarvis-draft` beside it displays streamed code. After complete output passes syntax/interface checks, the original source is atomically updated with review backups and fresh byte checks.
- **Completion:** Jarvis reads back the written file and reports the verification scope. The draft header is removed from a completed new script. Syntax validation is distinct from functional testing.
- **Interruption:** Partial drafts remain clearly labeled. Private `.jarvis-runtime/coding-streams` records store their owned path and hash. Resume uses them only if disk contents still match. Sidecar draft files are retained; completed sidecars may be reused after their hash is checked. They are Git-ignored along with stream metadata.
- **Concurrent edits:** If another editor changes a draft or the original during generation, Jarvis stops rather than overwriting those changes. Incomplete/truncated HTTP output is rejected, and invalid source never replaces an existing working script.

Do not run an incomplete draft. Loading/prompt processing can produce no source tokens for a substantial time; streaming displays source once generation begins. Task messages expose that phase and keep Stop available. File creation and editing use disk APIs and do not depend on typing into an IDE or guessing UI controls.
