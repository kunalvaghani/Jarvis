## Security and resilience findings

The [86-tool matrix](feature-matrix.md) records modes, API scopes, approvals and evidence. All names/signatures/typed dispatch paths were exercised with a fake backend; wrong scalar/list/boolean/default/unknown-field families are rejected before that backend. All names and invalid dispatch were exercised over the real wire. These are bounded type/boundary families, not a claim that infinite input combinations or all real Spotify business outcomes were exhausted.

Hardening includes exact official HTTPS/URI parsing, exact Spotify Windows application IDs, no foreground media keys, app-only audio selection across active outputs, fixed API/token origins with redirects refused, bounded JSON/response sizes, non-finite/malformed JSON rejection, search limit 10 and library batches 40. By-name play requires an exact title and requested artist, refuses ties, and never chooses an arbitrary first result. Playlist names with incomplete/ambiguous listings and inactive/restricted/ambiguous devices require clarification. Owner-only playlist writes check `/me` against the target owner. Collaboration changes are destructive and cannot make a playlist both collaborative and public.

Human PKCE login records account consent in Windows Credential Manager using the explicit WinVault backend, with no plaintext fallback or LLM auth tool. API calls check that consent, scopes and an opaque per-process credential binding. Host approval names an unverified account fingerprint, overwrites any model-supplied binding, and the child rechecks it before dispatch. Outer command policy denials are also checked before routing into MCP. Relinking during approval fails closed. Metadata remains untrusted; token values are scrubbed from results and errors. Fixtures cover token echo/exception leakage, metadata-as-instruction non-dispatch, wrong owner/scope/device, account drift, provider isolation and malformed/oversized JSON. Adversarial real-model/cloud end-to-end behavior is not certified by those fixtures.

The API permits one refresh after an explicit 401 and at most two read attempts for bounded Retry-After/502/503/504 cases. It never retries an arbitrary write after timeout/unknown success. API 403/429 does not silently switch providers. An actual disposable MCP child writes a fixture marker and disconnects before acknowledgment; reconnect/repair leaves exactly one marker, proving no tool replay in that scenario. Live disconnects during Spotify account writes were not attempted. A ping proves child responsiveness, not Spotify app/account readiness. Forced termination of every possible Windows launcher/descendant topology and sleep/wake behavior remain unqualified; the integration retains the existing bridge's process primitive.
